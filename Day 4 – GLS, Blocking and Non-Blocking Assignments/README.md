## 1. Gate-Level Simulation (GLS)

### Theory

Gate-Level Simulation is the process of simulating a synthesized netlist to verify the functionality of a digital circuit after synthesis.

Unlike RTL simulation, which operates on behavioral Verilog descriptions, GLS uses the gate-level netlist generated by the synthesis tool.

GLS helps verify whether the synthesized circuit behaves as expected.

### RTL Simulation vs Gate-Level Simulation

| RTL Simulation | Gate-Level Simulation |
|---|---|
| Uses behavioral RTL code | Uses synthesized gate-level netlist |
| Describes design functionality | Represents actual logic gates and cells |
| Generally faster | Generally slower |
| Does not require standard-cell models | Requires appropriate cell models |
| Checks RTL functionality | Checks synthesized implementation |

### Importance of GLS

- Verifies the functionality of the synthesized netlist.
- Helps identify synthesis-related functional mismatches.
- Checks the behavior of mapped standard cells.
- Helps detect issues that may not be visible during RTL simulation.

## 2. Blocking and Non-Blocking Assignments

### 2.1 Blocking Assignments (=)

Blocking assignments execute sequentially within an `always` block.

The next statement executes only after the previous assignment is evaluated.

**Syntax:**

```verilog
always @(*) begin
    a = b;
    c = a;
end
```

Characteristics:

- Uses the `=` operator.
- Executes statements in sequential order.
- Updates the assigned variable immediately within the procedural block.
- Commonly used in combinational logic.

### 2.2 Non-Blocking Assignments (<=)

Non-blocking assignments schedule updates for the end of the current simulation time step.

All right-hand-side expressions are evaluated before the scheduled updates take effect.

**Syntax:**

```verilog
always @(posedge clk) begin
    q1 <= d;
    q2 <= q1;
end
```

Characteristics:

- Uses the `<=` operator.
- Updates are scheduled rather than applied immediately.
- Commonly used in sequential logic.
- Helps model flip-flops and registers correctly.

## 3. Difference Between Blocking and Non-Blocking Assignments

| Blocking (=) | Non-Blocking (<=) |
|---|---|
| Executes immediately | Schedules updates |
| Statements execute sequentially | Updates occur at the end of the time step |
| Commonly used in combinational logic | Commonly used in sequential logic |
| Can cause race conditions if used improperly | Avoids many common sequential assignment race conditions |

## 4. Blocking Assignment Experiments

### Experiment 1: Blocking Assignment

Blocking assignments were studied to understand how procedural statements execute sequentially.

The values assigned to variables are updated immediately, affecting subsequent statements within the same procedural block.

### Experiment 2: Blocking Assignment in Sequential Logic

Blocking assignments were examined in clock-triggered processes to understand how immediate updates can affect the behavior of sequential circuits.

Using blocking assignments in sequential RTL can introduce simulation-order dependencies and race conditions.

## 5. Non-Blocking Assignment Experiments

### Experiment 1: Non-Blocking Assignment

Non-blocking assignments were studied to understand how register updates are scheduled during a clock event.

The right-hand-side values are evaluated before the scheduled left-hand-side updates occur.

### Experiment 2: Non-Blocking Assignment in Sequential Logic

Non-blocking assignments were used to model sequential circuit behavior.

They allow multiple registers to sample their previous values at the same clock edge, which correctly represents typical flip-flop behavior.

## 6. Simulation and Waveform Analysis

Icarus Verilog was used for RTL simulation, and GTKWave was used to analyze the generated waveforms.

The simulation process includes:

1. Compile the Verilog design and testbench.
2. Execute the generated simulation file.
3. Generate a VCD waveform file.
4. Open the waveform using GTKWave.
5. Observe signal transitions and compare assignment behavior.

### Commands Used

```bash
iverilog -o simulation.vvp design.v testbench.v
vvp simulation.vvp
gtkwave dump.vcd
```

The filenames should be replaced with the corresponding design and testbench filenames.
